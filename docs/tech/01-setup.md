## 2. Architecture

### 2.1 Context and constraints

The app is a desktop program for Windows, macOS and Ubuntu. It has no server, makes no network call of its own (PRD00-FR-12, PRD01-FR-14, BR-05, D15), keeps data on the machine (FR-15, BR-10), drives the person's own Claude Code and Codex programs (BR-01), and renders the approved HTML/CSS design system: `tokens.css`, bundled Be Vietnam Pro and JetBrains Mono, Lucide SVG icons, glass surfaces with `backdrop-filter` and a solid fallback.

### 2.2 Stack (decision T1, **decided**)

**Decided: Tauri 2** (Rust core, system webview, React + Vite + TypeScript renderer). Source: user decision (Tech lead: DaoNguyenTrong), 2026-11-27. Rationale given by the Tech lead: the approved HTML/CSS design system and boards stay as they are; installers are small; the operating system updates the webview; Tauri has a capability and permission model for what the renderer may call. Costs the Tech lead accepted: Rust for the core; three different webviews (WebView2, WKWebView, WebKitGTK); no WebDriver e2e on macOS. Native toolkits (one codebase per OS) were dropped without scoring: three codebases and no reuse of the HTML design system.

| Criterion | **A. Tauri 2 (chosen)** | B. Electron + TypeScript (rejected) | C. Native per OS (dropped) |
|---|---|---|---|
| Drive and supervise local programs | Rust `std::process` in the core; no shell plugin (§7.3). Process group (Unix) and job object (Windows) for the whole-tree kill | Node `child_process`: mature on all 3 OS | Three implementations |
| Design system fit | Three engines at different versions; `backdrop-filter` glass and Vietnamese diacritic rendering can differ, especially on WebKitGTK. Managed by spike V9, a build baseline (§8) and the system's own solid fallback | One bundled Chromium: identical rendering on all 3 OS. **The main merit of B** | Re-draw the design system |
| Test tooling | `tauri-driver` (WebDriver) on Windows and Linux only; **no macOS e2e**. Covered by §11.1 (Rust IPC tests, Playwright with a mocked IPC on three OS, manual macOS checklist) | Playwright `_electron` on all 3 OS, macOS included. **Second merit of B** | Per-OS automation |
| Installers | NSIS `.exe`, `.dmg`, `.deb` from the Tauri bundler; typically under 10 MB per app, **plus** the WebView2 runtime on Windows if absent (§10) | Chromium and Node inside: about 100 MB or more per OS | Per-OS packaging |
| Who patches the engine | The OS: Windows via the WebView2 Evergreen runtime, macOS via system updates, Ubuntu via `apt` security updates of WebKitGTK. Thermora ships Rust and Tauri fixes only (§7.9) | Thermora must ship a new installer for each Chromium and Node fix (7 and 30 day targets in the first draft) | The OS |
| Renderer isolation model | Capability and permission files, app manifest for own commands, CSP, no Node in the page (§2.3). Rust memory safety in the core | Sandbox + context isolation + preload; Chromium and Node attack surface to keep small | Smallest runtime, largest code |
| Language and toolchain | TypeScript renderer + Rust core: a second language and toolchain on every build machine | TypeScript only | Three |
| Offline and no-network posture | Engine callouts belong to the OS webview and cannot all be switched off from the app (§7.2, residual risks) | Chromium callouts (spellcheck download, component updater) switched off by the app | Fewest |

**Why B was rejected, so that it is not reopened without cause:** its strengths are one rendering engine, e2e on macOS and one language; against them the Tech lead weighed install size, the cost of patching a bundled Chromium by hand for a pilot with no update channel, and the capability model of A. The layering of §2.4 keeps `thermora-core` free of any UI-framework import, so a later move back is a rewrite of `src-tauri` only.

**Supporting choices** (same decision, lower stakes, easy to change before code exists): renderer in React and TypeScript, built with Vite; **Bun is used only as the JavaScript package manager and runner of the repo's own `scripts/`** (`bun install --frozen-lockfile`); no JavaScript runtime ships in the product, and the renderer's unit and component tests run on Vitest, not `bun test` (§11.1); e2e through `tauri-driver` with WebdriverIO and Playwright (§11.1); contract types generated from Rust by `ts-rs` (T8); Tauri 2 minor, the `tauri` and `@tauri-apps/api` pair, `wry` and the Rust toolchain pinned in lockfiles and `rust-toolchain.toml` at implementation time (§7.3, §7.9).

### 2.3 Components, processes and limits on the webview

```
┌────────────────────── Tauri app process (trusted, Rust) ───────────────────────┐
│ src-tauri     commands, caller check, capability files, window and webview     │
│               setup, event emit, sim and production composition roots          │
│   │ calls                                                                      │
│ crates/thermora-core   domain (rules) → application (use cases) →              │
│                        infrastructure: ProcessRunner, ProgramLocator,          │
│                        SettingsStore       (no Tauri dependency)               │
│ crates/thermora-os     the only `unsafe`: process group and job object         │
└───────▲──────────────────────────────────────────────────┬─────────────────────┘
        │ Tauri IPC: commands + events, typed, each command │ spawn, fixed argv
        │ granted by a capability file                      │
┌───────┴──────────────────────────────┐        ┌───────────▼──────────────┐
│ System webview: WebView2 / WKWebView │        │ claude / codex programs  │
│ / WebKitGTK; origin of the app       │        │ (the person's own, local)│
│ src/renderer: React + tokens.css     │        └───────────┬──────────────┘
│ no Node, no plugin API, no remote URL│                    │ only these talk
└──────────────────────────────────────┘                    ▼ to the AI service
```

Data flow of the module: the renderer asks for state; `thermora-core` locates each program, runs `--version` and the sign-in status command, maps results to the five states (§6.1) and the app crate pushes snapshots as events; the renderer only draws them. The core is the single source of truth for service state, choice and reminder; the renderer keeps the last snapshot and nothing else.

**How the renderer is limited** (appsec 4, 13, re-mapped to Tauri 2; the network side of the webview is §7.2):

1. **Only the app's own commands are callable.** Every command is declared in the app manifest (`build.rs`, `tauri_build::AppManifest::new().commands(..)`), which generates one `allow-<command>` permission per command; **a command that is not in the manifest is open to every window by default in Tauri 2, so the manifest is mandatory**. The single capability file `src-tauri/capabilities/main.json` lists the window `main` and grants exactly those `allow-` permissions plus `core:event:allow-listen` and `core:event:allow-unlisten`. **`core:default` is not used** (it pulls in window, webview, path, menu and tray permissions the app does not need); a window-control permission (for example start-dragging) is added only if the Design lead chooses a frameless window, and then one by one. A Rust test (§11.1) parses the capability and manifest files and requires that the set of `#[tauri::command]` names, the manifest list, the `invoke_handler` list and the granted permissions are the same set, that the only window is `main`, and that there is no `remote` entry.
2. **No plugin is exposed to the renderer.** Not granted and not registered unless needed in Rust: `shell`, `fs`, `http`, `opener` and `clipboard-manager` permissions, `dialog`, `process`, `updater`, `store`, `sql`, `stronghold`, `websocket`, `upload`, `log`. One plugin is used **from Rust only**, with no permission in any capability file: `tauri-plugin-clipboard-manager` (writes the core-built support text, C-11). **`tauri-plugin-opener` is not used** (appsec re-review 2): the URL opener is built inside the process module with fixed absolute paths (`/usr/bin/xdg-open` on Ubuntu, `/usr/bin/open` on macOS, `ShellExecuteW` in `thermora-os` on Windows), so no plugin and no plugin command exists for a page to reach (C-12). Justification: the page must not be able to open a URL or write the clipboard on its own (§7.2); the plugins' JavaScript commands stay denied because no capability grants them. The renderer package `package.json` has no `@tauri-apps/plugin-*` dependency (lint, §2.4).
3. **Caller check in depth.** The capability scopes by window label; every command additionally takes an `Authorized` argument (a custom `CommandArg` extractor) that rejects with `FORBIDDEN_SENDER` unless the calling webview label is `main` and its URL origin equals the app origin exactly (§5). A direct `#[tauri::command]` without the extractor fails a CI check (§11.1).
4. **Origin and content.** The UI is the packaged frontend served by Tauri's own custom protocol: origin `tauri://localhost` on macOS and Linux, `http://tauri.localhost` on Windows (`https://tauri.localhost` if `useHttpsScheme` is set; the exact constants are fixed in E1b and covered by a test). No dev server, no `file://`, no remote URL in a release build: no `remote` capability, no `devUrl` in the production config, no `assetProtocol` (disabled), `app.withGlobalTauri: false` (no `window.__TAURI__` global; the renderer imports the API module), `app.security.freezePrototype: true`.
5. **CSP in `tauri.conf.json` (`app.security.csp`):** `default-src 'none'; script-src 'self'; style-src 'self'; font-src 'self'; img-src 'self'; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'; form-action 'none'; frame-src 'none'; frame-ancestors 'none'; worker-src 'none'`. No inline script, no `unsafe-eval`. **The first draft's `connect-src 'none'` cannot be kept:** Tauri 2 sends its IPC through the `ipc:` protocol (`http://ipc.localhost` on Windows), which the page must be allowed to reach; that scheme is answered inside the app and is not a network connection. Tauri adds its own nonces or hashes to the injected scripts; `dangerousDisableAssetCspModification` stays off. A test compares the CSP string with the one above.
6. **Developer tools off in release.** The `devtools` Cargo feature of `tauri` is not enabled in the production profile and the window builder calls `.devtools(false)`; a CI check lists the resolved features of the release build and fails if `devtools` is on. Debug builds may have it.
7. **Navigation and new windows blocked.** The main window is created in code (`app.windows` is empty in `tauri.conf.json`), so the builder can set `on_navigation` to allow only the app origin, deny every `window.open` and new-window request (`on_new_window` where the pinned Tauri version has it; where it has not, the capability file grants no window-creation permission and Rust code creates no other window, which a test checks), Tauri's drag-drop handler left **on** (it consumes the drop; the default), or, if it is turned off, `preventDefault` on `dragover` and `drop` in the renderer and `on_navigation` denying `file:`; a test (§11.1 renderer and configuration layers) drops a file on the page and checks that the page does not navigate (appsec re-review 8), `incognito` or an equivalent so the webview keeps no persistent profile where the OS allows it (to confirm in V11), and a fixed webview data folder under the app's local data folder. No `<iframe>`, no `<webview>`.
8. **Isolation pattern considered and not used.** Tauri's isolation application would add a sandboxed iframe that can inspect each message, aimed at hostile frontend dependencies. Here the Rust core re-validates every request anyway (`serde` with `deny_unknown_fields` plus the rules of §3.2 and §5) and the renderer has a short dependency list (§7.9); the extra moving part and the loss of simplicity are not worth it now. Revisit if a renderer dependency is added that the Security owner is uneasy about.

### 2.4 Layers and dependency direction (proposal for `.claude/rules/architecture.md`)

Rust crates in one Cargo workspace; the renderer in `src/renderer`; generated types in `shared/contract`.

| Layer (path) | May depend on | Must never depend on |

| `thermora-core/contract` (DTO structs, error codes, state enums; `serde`, `ts-rs`) | nothing in the app | Tauri, any other layer |

| `src/renderer` | `shared/contract/generated`, `shared/locales`, React, `@tauri-apps/api` **only in `src/renderer/bridge/tauri.ts`** (a `Bridge` interface that tests replace with a fake) | Node, the plugin packages, any other path |

Enforcement (proposal): crate edges are enforced by `Cargo.toml` itself (`thermora-core` lists no `tauri` dependency; `cargo-deny` and a metadata test fail on a new edge); dependency-cruiser in CI for the renderer; a grep test that `@tauri-apps/api` is imported only by `bridge/tauri.ts` and no `@tauri-apps/plugin-*` appears in `package.json`. Invariants to list in `AGENTS.md` § Critical Invariants if confirmed: (1) no code reads, copies or parses a provider credential file or credential store (§7.1); (2) the only network path out of the app is the person's own AI program (§7.2).

### 2.5 Client-app statements (rule 10)

- **Shared vs per platform:** all code is shared. Per-OS data: program search locations, the install text, the sign-in capability table, installer format (§3.4, §10). Per-OS code, kept in two places only: the locator and runner differences, and the kill code in `thermora-os` (process group on Unix, job object on Windows). Per-OS **runtime**: the system webview (WebView2, WKWebView, WebKitGTK), which differs in version and in rendering; the renderer is built to a baseline that all three run (§8).
- **Offline and sync:** nothing syncs; there is no server. Offline only affects the provider checks (state *Cannot be checked*, AC-11). Conflicts cannot arise: data is on one machine (BR-10).
- **Minimum client version the API must serve:** Not applicable: no API and no server (§4 is a local IPC contract, always shipped together with the app that calls it).
- **OS permissions:** none requested: no camera, location, notifications, accessibility, file access beyond the app's own data folder. macOS may show a first-launch Gatekeeper prompt for the unsigned app (§10) and, to be checked (§14 V5), a Keychain prompt when the provider program reads its own login. Runtime prerequisites: WebView2 Runtime on Windows (§10, T17), `libwebkit2gtk-4.1` on Ubuntu 22.04 and later (a dependency of the `.deb`), WKWebView on macOS (part of the OS).
- **Store release and feature flags:** no store. Installers are handed over by the supporter (§10). No runtime feature flags; build modes only: Cargo features `sim` and `placeholder-ai` (§11.3, §6.5).

## 3. Data model

Everything is on this machine, nothing is shared (FR-15, BR-10, D10, AC-37).

### 3.1 Stored: `settings.json`

One JSON file in the app's data folder, resolved by Tauri's path resolver (`app_data_dir`) from the bundle identifier (proposal: `app.thermora.desktop`; sim: `app.thermora.desktop.sim`): `%APPDATA%\<identifier>\` on Windows, `~/Library/Application Support/<identifier>/` on macOS, `~/.local/share/<identifier>/` on Ubuntu. The webview keeps its own folder apart (`app_local_data_dir`, §2.3 point 7); Thermora stores nothing in it.

| Field | Type | Required | Limits and rules | Serves |
|---|---|---|---|---|
| `schemaVersion` | integer | yes | `1`. A reader keeps and writes back unknown fields, so a settings file written by a newer Thermora is never damaged by an older one | forward compatibility |
| `displayName` | string | yes after first run | 1 to 50 graphemes after trim, NFC (§3.2) | FR-01, BR-03 |
| `chosenService` | `"claude-code"`, `"codex"` or `null` | no | `null` until the person chooses | FR-07, D3 |
| `reminderSeenAt` | ISO-8601 UTC string or `null` | no | `null` = reminder not yet closed | FR-09, FR-15 |
| `createdAt` | ISO-8601 UTC string | yes | Set at first save; informational | — |

**File creation (appsec 9).** The settings file, its temp file, a corrupt file renamed to `settings.json.bad` and the `.bak` of a migration are created with `OpenOptions::create_new(true)` (`O_EXCL` / `CREATE_NEW`) and, on Unix, mode 0600 (`OpenOptionsExt::mode`) inside the data folder, so a pre-planted file or symlink makes the write fail instead of being followed. The temp file has a unique name (process id, time and a counter) so that a stale one after a crash does not block the next write. The write is temp file, `sync_all`, `fs::rename`. A failed write leaves the old file and shows no error detail.

**Not stored, by design:** the service state, versions, program paths and any last check result. Readiness is recomputed at every start and on request, so a stale "Ready" cannot exist (D2, §8 of the PRD). No sign-in detail of any kind (BR-02): there is no field for it and §7.1 forbids code that would hold one.

**Write rules.** Write to a temp file in the same folder, flush, then rename over `settings.json` (atomic); one writer (the Rust core, behind a mutex). Folder mode `0700` (`DirBuilderExt::mode`) and file mode `0600` on macOS and Ubuntu; on Windows the file inherits the user-profile ACL, which already limits it to the user (checked in §11). **Unreadable or invalid file** (parse error, wrong types): move it to `settings.json.bad-<UTC timestamp>` and start as a first run; never delete it, never crash, never fall back to guessed values. Fail closed: an invalid `chosenService` is read as `null`.

**History and delete.** No history. Uninstalling the app leaves the folder; removing it removes everything the module ever stored. The store for PRD02 data (history entries, projects) is decided in TECH-02 and is a separate file or database; the common part here does not constrain it, except that PRD02 must not put per-machine settings into packages (PRD01 §12).

### 3.2 Display name rule (BR-03)

Implemented **once**, in `thermora-core/domain` (Rust). The renderer does not re-implement it: it shows the live message by calling C-13 (a pure check, no state), and C-02 applies the same function before saving. One implementation also avoids relying on `Intl.Segmenter` and Unicode tables that differ between the three webviews. Crates: `unicode-normalization` (NFC), `unicode-segmentation` (graphemes), `unicode-properties` (general category). Test vectors live in `shared/contract/name-vectors.json` and are run by the Rust tests (and by the renderer's component tests through the fake bridge). The rule: trim Unicode white space at both ends; normalise to NFC (macOS input can produce decomposed Vietnamese letters; storing NFC makes equal names equal and gives one length); count user-perceived characters (extended grapheme clusters), so "Nguyễn" is 6 whichever way it was typed; accept 1 to 50. Reject empty, and reject control characters, line and paragraph separators, unassigned or private-use code points, and bidirectional override or isolate characters (U+202A to U+202E, U+2066 to U+2069), because the name will appear in history and in exported package origins and must not be able to reorder the text around it. Everything else printable is allowed (letters with marks, spaces, punctuation, emoji). No uniqueness check. Error codes: `EMPTY`, `TOO_LONG`, `INVALID_CHARS`. AC-02 to AC-05, AC-38. Vietnamese input with Telex or an IME is exercised in spike V10.

### 3.3 In memory only

`ServiceSnapshot` per service: `state` (`checking`, `ready`, `not_installed`, `not_signed_in`, `version_unsupported`, `cannot_check`), `version` (string or absent), `reason` (for `cannot_check`: `timeout` or `check_failed`), `checkedAt`. The in-use service is derived (§6.5), not stored separately.

### 3.4 Shipped inside the app, read-only: `resources/supported-versions.json` (BR-08, §12 of the PRD)

```json
{ "schemaVersion": 1,
  "services": {
    "claude-code": { "minVersion": "<set by spike V2>", "binaryNames": {"win32":["claude.exe"],"darwin":["claude"],"linux":["claude"]},
                     "signIn": {"win32":"handoff","darwin":"handoff","linux":"handoff"},
                     "help": {"win32": {...}, "darwin": {...}, "linux": {...}} },
    "codex":       { "minVersion": "<set by spike V2>", "binaryNames": {"win32":["codex.exe","codex.cmd"],...}, "signIn": {...}, "help": {...} } } }
```

- `minVersion`: the declared minimum (semver, §6.1 step 2). Until the spike sets it, the minimum is the first version that has the status command and a parseable `--version`; a version that cannot be parsed counts as unsupported (§14 Q2). The values are set in the PR that builds detection, from the spike that finds the first version having the status and login commands this design uses (§14 Q2). A version at or above the minimum is accepted; there is no maximum, because a newer version that changes the documented status commands shows up as `cannot_check` (§6.1), never as Ready.
- `signIn`: per OS, `launch` (FR-06 case a) or `handoff` (case b), the capability table of §6.3. Changing a cell is a data change, not a code change. **Every cell ships as `handoff` until spike V3 passes for that tool and OS** (§14 Q1, SA on behalf of user); a cell becomes `launch` only from a spike result.
- `help`: per OS, the text and link of the setup help: the install command for the supporter and the provider's official page (a fixed allow-listed URL, §7.3). Until spike V7, `help` holds the link to the provider's official install page and the install command the provider documents for that OS, confirmed by the supporter before release; the illustrative `npm install -g` of the boards is not used (§14 Q9, SA on behalf of user).
- It is compiled into the binary (`include_str!`, parsed at start), so no file path is opened at run time and the list travels with the installer (D15: no server). A new list means a new installer.

## 4. IPC contract (REL-1)

There is no HTTP API. The contract is between the renderer and the Rust core through **Tauri commands and events**. **Source of truth:** the Rust DTO structs and error enums in `thermora-core/contract`, which `ts-rs` exports to `shared/contract/generated/*.ts` (committed). The renderer's `Bridge` interface (§2.4) is written against those generated types. **Drift check (for `api-contract.md`):** a CI job regenerates the types and fails on any diff; the Rust command list, the app manifest and the capability file are checked for equality (§2.3 point 1). Every command parses its input with `serde` (`deny_unknown_fields`, enums for service ids), applies the rules of the core, and returns `Result<T, IpcError>` where `IpcError { code }` is a closed enum; nothing panics across the bridge (clippy denies `unwrap_used`, `expect_used` and `panic` in core and app crates). ## 5. Authorization

Thermora has no accounts, roles or permissions (PRD00-FR-01, BR-01; PRD01-AC-43): every person on the machine sees and may do the same. Authorization in this design therefore means two things, and both are enforced in the Rust core and the Tauri configuration, never by the UI.

1. **Who may call the core.** Only the app's own window (appsec 4). Three layers, each fail-closed:
   - *Capability:* the capability file `main.json` names the window `main` only and grants the app's own `allow-<command>` permissions and the two event-listen permissions (§2.3 point 1). A command not granted is refused by Tauri before the handler runs.
   - *Caller check in the handler:* every command takes an `Authorized` extractor, registered only through one macro (Appendix, §12.1), that requires the calling webview label to be `main` and the URL origin of that webview to equal the app origin **exactly** (the constant of §2.3 point 4, parsed with `url::Url` and compared as scheme, host and port, never by string prefix). Anything else, including a URL that cannot be read, returns `FORBIDDEN_SENDER` and nothing runs. Tauri also checks the origin of a calling frame against the capability; the design does not rely on that alone, and a test with a second window and an injected frame proves the denial (§11.1). The CSP forbids frames (`frame-src 'none'`), so a same-origin frame cannot exist in a release build.
   - *Content:* the UI is the packaged frontend on Tauri's own protocol; the app opens one window, never loads remote content, allows navigation only to the app origin, denies new windows, has no `<webview>` and no plugin exposed (§2.3). The renderer receives one typed function per command from the `Bridge`; it has no generic "invoke command X" helper in the app code (lint: `invoke` from `@tauri-apps/api` is called only in `bridge/tauri.ts` with a literal command name from the generated list).
2. **What state may change what.** Rules are in `thermora-core`, not in the renderer: `choose` needs the service to be `ready` at that moment (`SERVICE_NOT_READY` otherwise); `startSignIn` needs `not_signed_in`; `ai.requestPlaceholder` re-reads state and never trusts a state sent by the renderer. The renderer sends only the service id and the display name; it can never choose a program path, an argument or a file.

**Fail closed:** a missing or unreadable setting, an unknown service id, a `serde` parse failure, a failed caller check or an unrecognised sender denies; nothing falls back to allow. **OS-level scoping:** the settings file belongs to the OS user (§3.1); two OS users on one machine have separate data and separate provider sign-ins (BR-11).

**List queries:** none (no lists). **What a denial returns:** `FORBIDDEN_SENDER` or `INVALID_INPUT` as in §4.

## 6. Main flows (REL-1)

### 6.1 Detection of one service (FR-03, BR-05, BR-13, D2, D16)

Runs for both services at every start and when the person asks, in parallel. Each service has **one 10-second budget** for the whole pipeline (AC-39); each step gets what is left; when it runs out the running program's process tree is killed and the state is `cannot_check` with reason `timeout`, keeping any version already read (board 02, frame 3). The app stays usable meanwhile (checks run as async tasks in the Rust core, off the webview; the renderer only shows the `checking` state).

1. **Locate** (§6.2). Not found: `not_installed` (AC-08, AC-13).
2. **Version.** Run `<program> --version`. Take the first `x.y.z` (optionally with a pre-release tag limited to `[0-9A-Za-z.-]{1,32}`; a longer tag or other characters make the version unparseable, so nothing else reaches the screen or the copied text, appsec 10) from the first line of output; compare with `minVersion` by semver (pre-release is lower than the release). A non-zero exit: `cannot_check` / `check_failed`. Exit 0 with no parseable `x.y.z`: counts as unsupported (`version_unsupported`) until spike V2 fixes the real output format (§14 Q2, SA on behalf of user). Below minimum: `version_unsupported` (AC-10). This step is read-only by contract.
3. **Sign-in status.** Claude Code: `claude auth status`; Codex: `codex login status`. **Only the exit code is read**: 0 means signed in, 1 means signed out, anything else (other code, signal, spawn failure) is `cannot_check` / `check_failed`. Standard output and error are drained into a small bounded buffer and discarded unread (§7.1); the JSON `claude auth status` prints is not parsed. Signed in: `ready` (AC-07). Signed out: `not_signed_in` (AC-09).

Nothing other than these three argument lists plus one more typed entry, the login-shell PATH read of §6.2 step 3 (appsec 6), plus the two URL-opener argument lists of §7.2 (`/usr/bin/xdg-open <URL>`, `/usr/bin/open <URL>`) (together the **detection allow-list**, a typed constant) can be passed by this pipeline, so by construction it sends no prompt to the AI (AC-28 start-up half). The same allow-list is the unit-test target and the argv test (§11.2). Detection keeps the whole-tree kill on timeout. Sign-in programs are different (§6.3).

### 6.2 Locating a program (FR-03, §8 of the PRD "tool in an unusual place")

A GUI app started from Finder, the Dock or the Ubuntu launcher does not inherit the person's terminal `PATH`, so a plain `PATH` lookup would say "Not installed" for a program that works in the terminal. Search order, first existing regular executable file wins, **always resolved to an absolute path**:

1. The app's own `PATH` (on Windows this is the full user environment). **In every step, an entry that is not an absolute path (empty, `.`, relative) is dropped** (appsec 5).
2. Known install directories per OS: Windows `%USERPROFILE%\.local\bin`, `%APPDATA%\npm`, `%LOCALAPPDATA%\Programs`; macOS and Ubuntu `~/.local/bin`, `~/.claude/local`, `/usr/local/bin`, `/opt/homebrew/bin`, `/usr/bin`, the npm global prefix `~/.npm-global/bin`. (Directory list to be confirmed by V7.)
3. macOS and Ubuntu only, once per start: the person's login-shell `PATH` (covers nvm, fnm, asdf and Homebrew set up in profile files). `$SHELL` is used only if it is an absolute path, is listed in `/etc/shells` and passes the trust check below; otherwise this step is skipped. The command is the fixed string `$SHELL -l -c 'printf %s "$PATH"'`, an entry of the typed allow-list (§6.1) and of the argv test; stdin is closed, output goes through the bounded buffer, and the process group is killed at 3 seconds. Output that is not a plain `:`-separated list of absolute paths is ignored (appsec 6).

Never searched: the current directory (Windows resolves a bare name by its own search order, which includes directories Thermora does not control, which is why a bare name is never spawned) and any directory writable by other OS users. A tool in a place none of these find is shown as *Not installed*, as the PRD accepts (§8). The health-check text deliberately omits paths (design call 10). On Windows, a `.cmd` shim (npm installs of Codex) is run as in §7.3.

**Trust check on the chosen program (appsec 5).** On macOS and Ubuntu a candidate is rejected when the file or its folder is not owned by the current user or root, or is writable by group or others; a rejected candidate counts as not found for that path and the search goes on. **Symlinks (appsec re-review 4):** the locator may call `symlink_metadata` and `canonicalize` as well as `metadata`; it checks **every symlink hop** and the **folder of the final target** with the same ownership and mode rules, and spawns the **resolved path**, never the link, so a link checked once cannot be re-pointed before the spawn (a Homebrew or nvm link to a root-owned or user-owned folder passes; a link into a folder writable by others is rejected). On Windows no ACL check is made in REL-1 (it would need an extra spawn or native code): the residual risk is recorded in §7.6. **Environment variables read by Thermora** (the complete list, appsec 11): `PATH`, `SHELL`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA` (`HOME` only inside Tauri's path resolver); every other variable is neither read nor logged, and the child environment is passed on unchanged, with one **named exception**: on Windows `NoDefaultCurrentDirectoryInExePath=1` is set for the child (or non-absolute `PATH` entries are stripped, §7.3; appsec re-review 3).

### 6.3 Sign-in (FR-06, AC-14, AC-15, AC-16) and the case a or b recommendation

**What happens in case a** (C-05, capability `launch`): `core` spawns the provider's own program with fixed arguments, `claude auth login` or `codex login`, with **standard input, output and error all discarded** (`Stdio::null()` for the three) and no console window (`CREATE_NO_WINDOW` through `CommandExt::creation_flags` on Windows). The provider's program opens the person's default browser on the provider's own page and runs its own callback; the person signs in there. Thermora never sees the address, the code or any token, because it never reads the program's output. While the program runs the UI shows the waiting block (board 04, frame 2). One sign-in per service at a time.

**Ends.** (1) The program exits with code 0: `core` pushes `signin.ended / finished` and runs the free check of §6.1 for that service; `ready` shows board 04 frame 4 (decision recorded in §14 Q6, SA on behalf of user: the re-check is automatic, the "Kiểm tra lại" button stays, and Ready is never claimed from the exit code alone). (2) Exit non-zero, spawn failure, or the program exits at once with no browser: `failed`, and the UI **degrades to case b** (board 04 frame 5) for that attempt, so a (tool, OS) pair where case a does not work still ends in a screen the PRD allows (AC-14 case b). (3) No end within 5 minutes, the person presses "Huỷ", or the app quits: **the outcome that must hold is that no provider login process remains, port 1455 is free, and the browser the program opened survives** (appsec 7, appsec re-review 1). The mechanism serves that outcome and is not the requirement: the login program is started in its own process group (Unix) and `core` first sends a graceful `SIGTERM` to that group (launchers such as npm shims forward signals to their child), waits a 2 s grace period, then escalates to `SIGKILL` of the group; the browser is started by the OS URL handler and is not in the group (V3 checks it for each cell). On Windows the launcher chain `codex.cmd` -> `cmd.exe` -> `node` -> `codex.exe` must end too: the candidate mechanisms are a job object (only if V3 shows the browser is not inside it) or ending the descendants of the direct child found at cancel time, never a browser image; V3 decides which. A (tool, OS, install type) cell that cannot meet the outcome stays `handoff` and is recorded as residual risk R-S10 (§7.6); `timed_out` or cancel returns to the "half-done" frame (board 04 frame 3, AC-16): state still `not_signed_in` and the same steps. If the person finished in the browser after the program was killed, the next check says `ready`. The state shown after any of these always comes from a fresh §6.1 check, never from the exit code of the login program.

**Case b** (capability `handoff`, or the degrade above): no process is started; board 04 frame 5 shows the steps and the text for the supporter (§6.6). The text contains no instruction to send a password or code to anyone (board call 8).

**Why not device auth for Codex.** `--device-auth` is beta, must be enabled in the person's account security settings, and it prints a code that has to be shown to the person to type on another page: that means reading the program's output and displaying a sign-in detail, against BR-02 and AC-15. Rejected.

**Recommendation per tool and OS** (case a is allowed by the PO, §14 Q3; each cell still waits for spike V3):

| Tool | Windows 10/11 | macOS | Ubuntu desktop |
|---|---|---|---|
| Claude Code (`claude auth login`) | a (browser opens from a background process; the manual code step is needed only when the callback cannot reach the machine, which does not apply to a local desktop) | a | a; needs `xdg-open` and a default browser, present on a desktop install; otherwise degrade to b |
| Codex (`codex login`, localhost:1455) | a; a second program already using port 1455 makes it fail, which degrades to b | a; same port note | a; same notes |

Both tools are recommended as **case a on all three OS, with the automatic degrade to case b and the `signIn` capability table as a switch per cell**, but **every cell ships as `handoff` until spike V3 passes for it**, and any doubt in detection ends as `cannot_check`, never Ready (§14 Q1, SA on behalf of user). Confidence is medium: the commands are official, but none of it was run here. If V3 fails for a cell, that cell stays `handoff` (a data change) and no board or code changes. The PO allowed case a (§14 Q3, 2026-11-27); the spike gate is the only remaining condition.

## 7. Security and privacy (needs appsec review)

This is the part `appsec` reviews first (round 2, after the move to Tauri 2). The common part and REL-1 touch a security area (the sign-in of the person's AI service; spawning local programs). There are no Thermora credentials and no tokens of Thermora's own: the security question is how the app behaves next to someone else's credentials.

### 7.1 Assets

| Asset | Where it lives | What Thermora does with it |
|---|---|---|
| Provider sign-in (OAuth tokens, API keys) | Provider-owned: Keychain, `~/.claude/.credentials.json`, `~/.codex/auth.json`, keyring | **Nothing.** Never opened, read, copied, listed, parsed, packaged or sent (BR-02, PRD00-FR-11). Not even to test that it exists: sign-in state comes only from the provider's own status command |
| Sign-in page address and one-time code | Printed by the provider's login program | Never captured: output of the login program is discarded (§6.3) |
| Plan quota | The person's subscription | Not touched by detection (BR-13); the placeholder starts no AI request |
| `settings.json` (name, choice, reminder) | The app's data folder | Low sensitivity; protected by file mode (§3.1) |
| Integrity of the app and of the program it runs | Installer and the person's installation | §7.4 |
| Webview profile (cache, local storage) | The webview's own folder | Holds nothing sensitive: the renderer stores nothing in it (no `localStorage`, no cookies, no IndexedDB), and a non-persistent profile is used where the OS allows (§2.3 point 7) |

**Enforcement of the invariant, in code** (appsec 1). The denial list is only a tripwire: it finds careless code and cannot see a path that is built at run time. The controls that count are (2) to (5).

1. **Denial list test:** a CI test fails if any source file under `src/`, `src-tauri/`, `crates/` or `shared/` (and `Cargo.toml` and `package.json` files) contains `.credentials.json`, `auth.json`, `.codex`, `.claude/.credentials`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `Keychain`, `security find-generic-password`, `secret-tool`, `cmdkey`, `CredRead`, `CredEnumerate`, `CryptUnprotectData`, `keyring`, `libsecret`, `secret-service`, `secret_service`, `org.freedesktop.secrets`, `SecItem`, `security-framework`, `oo7` or `stronghold`.
2. **Crate and plugin deny list:** `cargo-deny` `[bans]` forbids, anywhere in the production dependency graph, `keyring`, `secret-service`, `oo7`, `security-framework` (unless it arrives only through a crate the Security owner has reviewed), `tauri-plugin-stronghold` and every Tauri plugin except the one of §2.3 point 2 (`tauri-plugin-opener` is denied too). The layer rules of §2.4 apply: the renderer has no way to reach Rust file access.
3. **Lint on file access (Rust):** the workspace `clippy.toml` lists `disallowed-methods` for `std::fs::*` (read, read_to_string, read_dir, metadata, symlink_metadata, canonicalize, `File::open`, `OpenOptions::open` and the rest), `tokio::fs::*`, `std::path::Path::exists`, `is_file`, `is_dir` and `try_exists`. The only places with `#[allow(clippy::disallowed_methods)]` are `infrastructure/settings` and `infrastructure/locator` (a grep test lists every `allow` of these lints and fails on any other file). The locator may call only `metadata` (stat), `symlink_metadata` and `canonicalize`, and only on a path produced by one path-builder function from a fixed directory list plus a `binaryNames` entry (§3.4, §6.2); the settings module may open only its own folder (`app_data_dir` plus three fixed file-name patterns). No other string may reach a file call. The `fs` plugin is not installed, so the renderer has no file access either.
4. **Runtime proof:** a file-access trace (`strace -f -e trace=openat,stat,access` on Ubuntu, `fs_usage` on macOS, filtered to the Thermora process tree, which includes the webview helper processes; on macOS the WebKit helpers run under `launchd`, not as children, so `fs_usage` and `nettop` are also filtered by the process names `com.apple.WebKit.WebContent` and `com.apple.WebKit.Networking`, appsec re-review 6) in spike V1 and in the CI network job (§11.1) fails if those processes open anything under a provider configuration folder beyond a `stat` of the program files. Windows is traced with Process Monitor in V1 and before each release (manual, not in CI). **A limit of the trace, recorded honestly:** a credential-store access that an OS service makes on the app's behalf (the Keychain through `securityd`, the Secret Service through D-Bus) is not visible as a file open by the app; V1 adds `dbus-monitor` on Ubuntu (no call to `org.freedesktop.secrets`) and V5 checks that no Keychain prompt appears on macOS, and the crate and denial lists of (1) and (2) are the control against code that would ask for it.
5. **Dependency allow-list:** the runtime `dependencies` of `thermora-core` and `src-tauri` are a short list kept in the repository (at first: `tauri`, `serde`, `serde_json`, `ts-rs` (build or test only), `semver`, `url`, `unicode-normalization`, `unicode-segmentation`, `unicode-properties`, `tokio` (as Tauri's runtime, process and time features only), `libc` or `nix` and `windows-sys` in `thermora-os`, `tauri-plugin-clipboard-manager`); a CI test compares `cargo metadata` and the renderer's `package.json` `dependencies` (React, `react-dom`, `@tauri-apps/api`) with it, and adding one needs the Security owner in the PR (§7.9).
6. The child environment is passed through unchanged and never read or logged by Thermora, apart from the five variables of §6.2 (clippy bans `std::env::var`, `var_os` and `vars` outside a typed `EnvReader` in the locator that names the five), so the provider's own variables reach the provider's own program and nothing else.

### 7.2 Network posture: nothing leaves except through the person's AI program (BR-05, PRD00-FR-12, D15)

**The app's own code makes no connection, and the system webview is kept from making any, as far as the OS allows. Some things cannot be switched off from the app; they are listed as residual risk below and in §7.6.**

*Thermora's own code.* Switched off or absent: updater (`tauri-plugin-updater` is not installed; Tauri's updater is not used, FR-14 and D15), crash reporter, telemetry, `log` plugin, any "check for updates" menu. Two enforcement layers (appsec 3), plus a third at run time:
- **Lint and dependency bans, Rust.** `clippy.toml` `disallowed-types` and `disallowed-methods` ban `std::net::*` (`TcpStream`, `TcpListener`, `UdpSocket`, `ToSocketAddrs`), `tokio::net::*` and every constructor of an HTTP client in the app crates. `cargo-deny` `[bans]` forbids `reqwest`, `hyper`, `hyper-util`, `ureq`, `isahc`, `curl`, `attohttpc`, `surf`, `native-tls`, `rustls`, `openssl`, `tungstenite`, `tokio-tungstenite`, `trust-dns-*` and `hickory-*` in the production graph. If the pinned Tauri pulls one of them transitively, the build fails and each exception is listed in `deny.toml` with a reason and the Security owner's approval (to find out when scaffolding, E1b; the check runs on the release feature set, so crates that only Tauri's debug features pull in do not count).
- **Lint, renderer.** `no-restricted-globals` and `no-restricted-imports` ban `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon`, `@tauri-apps/plugin-*` and the `@tauri-apps/api/*` modules other than `core` and `event` (so no `http`, `shell`, `fs` imports); CSP `connect-src` is limited to Tauri's IPC protocol (§2.3 point 5). A built-bundle grep fails on any `http://` or `https://` literal in the renderer other than the W3C XML namespace strings of the SVG icons; the two provider URLs live in Rust only.
- **Run-time proof, CI network job** (Ubuntu and macOS, Windows when a runner permits; the sim build): the app runs as a **dedicated OS user** while an OS firewall rule rejects and counts every outbound packet of that user except loopback (`nft` or `iptables` `-m owner --uid-owner` on Ubuntu, `pf` with `user` on macOS, Windows Firewall rule on Windows), together with a connection trace (`strace -f -e trace=connect,sendto`, `nettop` or `lsof -i`, ETW or `netstat`). The job fails on a counter above zero or any attempt. Blocking by user rather than by process matters: the webview's network and helper processes (`WebKitNetworkProcess` on Linux, `msedgewebview2.exe` on Windows, `com.apple.WebKit.Networking` on macOS) are separate processes that a rule on the main process would miss. A recording proxy is not used: it sees only traffic that honours the proxy. What the job cannot see is traffic by system services outside the user (below).

The product promise (BR-05) is worded for Thermora and the person's AI program; the PO confirmed that the rule covers Thermora's own code and processes only, and the user-facing wording is "Thermora tự nó không gửi gì, trừ tới dịch vụ AI của bạn." Spellcheck: WebView2 and WebKitGTK spell-check locally; the name field uses `spellcheck="false"` and `autocomplete="off"` so no content goes to a cloud spellcheck or autofill (a Windows setting can enable Microsoft Editor on Edge; for WebView2 this is not applied; V11 observes).
- The only outgoing action initiated by the person is opening a fixed provider help page in their browser (C-12): the Rust command calls the opener built in the process module with one of **two compile-time `https` URL constants chosen by service id** (never starting with `-`); the renderer cannot send a URL and has no opener permission. ### 7.3 Spawning programs (threat: command injection, path hijack)

Spawning is done only with `std::process::Command` (or `tokio::process::Command` with the same rules), constructed in one module of `thermora-core/infrastructure`; clippy `disallowed-methods` bans `Command::new` everywhere else and a grep test lists the `allow` sites. **`tauri-plugin-shell` is not used.** Its scope list is a good mechanism, but the plugin resolves commands by name, exposes a spawn command to the page unless every permission is withheld, and gives nothing the typed argument lists of §6.1 do not already give. The renderer has no shell access of any kind.

| Attacker | Attack | Mitigation |
|---|---|---|
| Content in the renderer (a bug, a future compromised dependency) | Make the core run another command or pass its own arguments | The renderer sends only service ids and a name; argument lists are typed constants (§6.1 allow-list, §6.3 two sign-in lists); `serde` with `deny_unknown_fields`; no string from the renderer or from a file reaches an argument list or a path; no shell or `fs` permission exists in the capability file (§2.3) |

### 7.4 Installer integrity (unsigned pilot installers, release plan distribution constraint)

Unsigned installers cannot prove who built them, and the operating system will warn (§10). The Tauri bundler produces them (NSIS `.exe` per user, `.dmg` ad-hoc signed, `.deb`); **the updater plugin and its signing key are not used** (FR-14, D15). Mitigations within the PO's decision (appsec 8): the installer file name carries the version; the release workflow publishes build provenance for every installer with `actions/attest-build-provenance`; on **each target machine, before the installer runs**, the supporter verifies it with `gh attestation verify <file> --repo <owner>/<repo>` or, where `gh` is not available, compares the SHA-256 shown in the CI run (`Get-FileHash` on Windows, `shasum -a 256` on macOS and Ubuntu) with the file, the CI run being a channel separate from the file handover. The supporter installs by hand from a verified file. `xattr -dr com.apple.quarantine` is run only on a `Thermora.app` that comes from a verified `.dmg`. The Windows installer with the offline WebView2 package (§10) is large; its hash is checked the same way. Residual risk: provenance shows which workflow built the file, not that the code was reviewed; someone who controls the repository's workflow or the CI run page defeats it. Accepted for a five-person pilot; the revisit trigger is the PO's (anyone other than the PO installs, or wider rollout).

### 7.5 What must never be logged or shown

No credential-like value, no program output, no environment, no program path in anything the person copies, no content of the person's files. **No log file is written in REL-1**; the Tauri `log` plugin is not installed; development builds log to the console with state codes only. A future log file requires amending this section and appsec review.

### 7.6 What an attacker on the machine gains

An attacker running as the same OS user can already read the provider's credential files and drive the provider's program directly; Thermora gives them nothing more: it stores no secret, and its settings file holds a display name, a choice and a date. They can change `settings.json` (a different name, a different chosen service), which affects only that person's own history labels, as the PRD accepts (PRD00-BR-11: no protection against outside changes). They can plant a program early in the search order (§7.3): equal to existing user-level compromise. Another OS user on the same machine has no access to the first user's data (file modes, separate provider sign-ins). Someone with physical access to an unlocked session is out of scope. A local process, also one of another OS user, racing the provider's own login callback on `localhost:1455` (the port is shared across OS users on one machine) is the provider's design; Thermora relies on the provider's PKCE and state check and tests it in spike V3 (appsec 12).

**Residual risks recorded (Security owner to accept with the document):**
- **R-S1 Windows, no ACL check** of the program's folder in REL-1: a program planted in a folder writable by other accounts or groups would be started; accepted for a five-person pilot and revisited with the first non-pilot user.
- **R-S2 WebView2 updater and diagnostic data** (§7.2): Microsoft's runtime updater and the runtime's diagnostic data are outside the app's control; they run independent of Thermora. Accepted by the PO as outside the no-network rule (§14 Q12, 2026-11-27).
- **R-S3 Webview engine variance:** the renderer runs on three engines at versions the OS decides. A machine whose OS is not updated (or cannot update, being offline) keeps an old webview with known flaws. Mitigations: no remote content, strict CSP, no navigation; `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` or a machine policy can add arguments such as `--remote-debugging-port` to the Windows webview from outside the app (appsec re-review 9; the app cannot prevent it, and it needs the person's own account or an administrator); the release checklist records the engine version on each pilot machine; a machine below the engine baseline of §8 is not supported.
- **R-S4 Linux webview process sandbox:** whether WebKitGTK runs the web process in its own OS sandbox depends on wry's setting and the distribution; the design does not assume it. The capability, CSP and no-remote-content layers carry the load. Confirmed or refuted in E1b.
- **R-S5 macOS ad-hoc signature** gives no publisher identity (§7.4).
- **R-S6 Zero-connection check scope:** the CI job proves Thermora's user makes no connection; system services (OS updaters, the WebView2 updater, Apple services) are outside it. Accepted by the PO (§14 Q12).
- **R-S8 Port-1455 race:** a local process (also of another OS user) can listen on `localhost:1455` before the provider's login does; Thermora relies on the provider's PKCE and state check and cannot test more than V3 does (appsec re-review 10).
- **R-S9 Login-shell PATH read** (macOS, Ubuntu, §6.2 step 3) runs the person's own profile scripts, which may open network connections; Thermora cannot prevent or see this, and the zero-connection check of §7.2 treats it as outside scope for that one spawn (appsec re-review 10).
- **R-S10 Left-over login process:** for a (tool, OS, install type) cell where the outcome of §6.3 (no login process left, port 1455 free) cannot be met, the cell stays `handoff`; until V3 has covered every cell, a cell shipped as `launch` is accepted only with the Security owner's agreement (appsec re-review 10).
- **R-S7 Tauri, wry and Rust crates** are a larger supply chain than the first draft's Node set; mitigated by §7.9, not removed.

### 7.7 The placeholder AI action

C-08 starts no program and sends nothing (§6.5), so REL-1 cannot spend a person's plan or send content. It is behind a build constant (the Cargo feature `placeholder-ai`) and is deleted when PRD02 delivers real actions; the test of §11.2 fails the build if C-08 is reachable in a production bundle after that replacement.

### 7.8 Provider terms (PRD01 §1, D19, §13 risks R1 and R2)

Designed to the PO's hard rules: only the official unmodified program is driven (BR-01); sign-in happens in the provider's own flow and Thermora cannot see it (BR-02); no sharing of a person's sign-in (BR-11). The one place where Thermora acts on the person's behalf is starting the provider's own login program (§6.3): the PO allowed it (§14 Q3), and the design keeps each cell a data switch gated by spike V3.

### 7.9 Supply chain and patching (appsec, missing part b)

- **Frozen installs.** Rust: `Cargo.lock` is committed and every CI build and test uses `--locked`; a job fails if the lockfile would change. JavaScript: `bun install --frozen-lockfile`. A dependency change is always visible in the PR diff.
- **Dependency checks.** `cargo-deny check` (advisories from the RustSec database, bans of §7.1 (2) and §7.2, licences, `sources`: crates.io only, no git or path dependencies outside the workspace) on every PR, and the same scheduled weekly (so an advisory published after merge opens an issue); `cargo audit` may run as a second source. `bun audit` (or the package manager's equivalent) for the renderer's few packages on the same schedule.
- **Build-time code is the install-script risk of Cargo.** `build.rs` scripts and procedural macros of every dependency run on the build machine. Policy: the set of crates in the graph that have a `build.rs` or are proc-macros is generated from `cargo metadata` and kept in the repository; a change to that set needs a one-line reason in the PR and Security owner review. `tauri-build`, `wry` and `tao` are the expected members. For npm: no dependency install script runs by default (`trustedDependencies` starts empty; each entry needs a reason and Security owner review); the `@tauri-apps/cli` binary package is expected to need none and is verified in E1a.
- **Runtime dependencies** of the Rust core and app are limited by the allow-list of §7.1 (5); the renderer has three.
- **Who patches what, and how fast (proposal; the Tech lead and Security owner confirm with this document).** *Webview engine:* patched by the OS vendor (Microsoft for the WebView2 Evergreen Runtime, Apple with macOS, Canonical through `apt` for WebKitGTK); Thermora ships nothing for it, and the release checklist records the engine versions seen on each pilot machine. A fixed-version WebView2 runtime would put that patching on Thermora and is rejected (T17). *Thermora's own stack* (Tauri, wry, tao, Rust crates, the Rust toolchain): a new installer within **7 days** of an advisory that is actively exploited, or critical and reachable in this app; within **30 days** for other advisories on a crate in the shipped graph (weekly scheduled check); the supporter hands the new installer to the five machines. Tauri, `wry` and the Rust toolchain version are reviewed at the start of every sprint, and a Tauri minor that has left the project's supported window is a blocking item (decision T15). Rust standard-library security releases (the BatBadBut class) raise the toolchain floor of §7.3.
- **`.deb` maintainer scripts:** **none** (the Tauri bundler does not need `chrome-sandbox` set-uid, which Electron did). A CI test lists the maintainer scripts of the built package and fails if any exist.

### 7.10 Sim build cannot become an installer (appsec, missing part c)

The `sim` build (§11.3) is the app crate built with the Cargo feature `sim` and a separate Tauri config file (`tauri.sim.conf.json`, merged with `--config`) that has its own `identifier` (`app.thermora.desktop.sim`), `productName` (`Thermora SIM`) and so its own data folder, so it can never replace or share data with the real app; the config has `bundle.active: false` (no installer target) and the CI builds it with `--no-bundle`. The feature `sim` is never in `default`. A CI check fails if an installer artifact or a release asset carries the sim identifier, if the production configuration names the sim identifier, if the release build's resolved features include `sim`, or if the production binary contains the sim module's marker string.

## 8. UI: fitting the design (REL-1)

**Renderer:** React and TypeScript, built by Vite for the **engine baseline** (the oldest WebKit in the pilot matrix: WebKitGTK of Ubuntu 22.04 and the WebKit of the oldest supported macOS, and the current WebView2): `build.target` is set to that baseline, a build-time check (browserslist plus a compatibility lint) fails on a CSS or JavaScript feature the baseline lacks, and PostCSS autoprefixer adds `-webkit-backdrop-filter` where needed without editing the system's CSS. No `Intl.Segmenter` or other newer API for rules that matter (the name rule runs in Rust, §3.2). Spike V9 fixes the baseline and the glass fallback. The stylesheet entry imports `docs/design/system/tokens.css` content copied at build into the renderer bundle together with the bundled Be Vietnam Pro 400/500/600/700 and JetBrains Mono, and the used Lucide SVGs (all local, nothing from a network, system README call 13). Screens use the role names of the tokens and the components of the system; no screen has CSS of its own (the boards follow the same rule). Light and dark follow the system's own tokens; theme selection is not decided by the system and defaults to following the OS (open for the Design lead, no REL-1 AC depends on it).

**State on the client:** one `useServices()` hook that calls C-03 and subscribes to E-01 through the `Bridge` (§2.4); `useProfile()` for C-01; no other global state. Loading is the `checking` state, never a blocking spinner.

## 9. Performance and scale (REL-1)

- Volumes: two services, one settings file of under 1 KB, no lists.
- **10 seconds per service** is the hard limit (D2, AC-39); a normal check is two short `--version` and status runs, expected under 2 seconds each (to be measured in V1).
- Both services check in parallel; the UI is never blocked (checks live in the Rust core, not in the webview).
- Program output is capped at 64 KB per run. The sign-in program runs at most 5 minutes.
- Start-up target: window visible with the `checking` state in under 2 seconds on a 2020 office laptop (target, measured in the e2e run, not an acceptance criterion).
- Install size: the app itself is small (the Tauri bundle, typically under 10 MB, to measure in E3); on Windows the installer is about 130 MB larger because it carries the offline WebView2 installer (T17). Memory and start-up depend on the system webview and are measured in V9. No background jobs, no timers except the 10 s, 3 s and 5 min limits above.

**WebView2 on Windows: install mode chosen (T17).** The no-network rule and Windows machines that may be offline make the choice matter. ### 11.3 Simulated machine states for the REL-1 demo

The demo needs "both Ready" and "none Ready" (release plan note) on a machine that may have the real tools. **There is no simulation switch in the product.** A separate build, the app crate with the Cargo feature `sim` (§7.10), swaps the composition root's `ProgramLocator` and `ProcessRunner` for a scripted pair that reads a scenario file (`both-ready`, `none-ready`, `claude-ready-codex-old`, `offline`, `slow`, `signed-out-then-in`) and uses a separate data folder, so the real settings are untouched. The `sim` module is compiled only under `#[cfg(feature = "sim")]` and the feature is never in `default`; a CI test fails if the production binary contains the sim module. The sim build has its own identifier and name and no installer (`--no-bundle`, §7.10). The e2e suite (`tauri-driver`, Windows and Ubuntu) and the PO's demo use the sim build (not an installer for other people); the Playwright renderer-level tests replay the same scenarios through `mockIPC`; one extra demo on the real tools proves the real path. Fake programs of §11.1 and the sim runner share the scenario fixtures.

### 12.1 Proposed content of `.claude/rules/authentication.md` (appsec, missing part a)

Proposal only. The file is filled in by `implementer` in the first implementation PR (enabler E1a), not in the docs PR that carries this design.

> **Authentication and credentials (Thermora)**
>
> 1. Thermora issues, stores, verifies and refreshes **no credential**: no account, session, token, cookie, password or API key of its own (PRD00-FR-01, BR-01, PRD01-AC-43).
> 2. **Provider sign-in is never touched.** No code reads, opens, copies, lists, parses, packages, logs or sends a provider credential file, credential store or credential variable (names: see the denial list of TECH01 §7.1). No credential-store crate or Tauri plugin is a dependency. Whether a service is signed in comes only from the exit code of the provider's own status command.
> 3. **The spawn points are exactly four:** `ProcessRunner` (detection: `--version` and the status command), the sign-in launch (`claude auth login`, `codex login`, only when the capability is `launch`), the login-shell `PATH` read (macOS, Ubuntu), and the fixed provider help-page opener (one of two compile-time URLs; `/usr/bin/xdg-open` or `/usr/bin/open` from the process module, `ShellExecuteW` in `thermora-os`; never a URL from the renderer, no opener plugin). A new spawn point needs an amendment of the technical design, `appsec` review and a tier-2 PR.
> 4. **Spawn rules:** `std::process::Command` only in the one process module; absolute path from the locator; no shell and no shell plugin (only the Windows `.cmd` rule of TECH01 §7.3, on Rust at least 1.81.0); `raw_arg` banned; argument lists are typed constants, nothing from the renderer or a file; stdin null; output bounded and discarded unread; detection kills the whole tree on timeout (process group, job object), the sign-in program ends its own login processes by outcome (no process left, port 1455 free, browser alive; §6.3).
> 5. **Fail closed, and the renderer is limited by configuration.** Every command is declared in the app manifest and granted in the single capability file of window `main`; `core:default`, the shell, fs, http, opener, clipboard and updater permissions are never granted; no remote URL, no `devUrl` and no devtools in a release build; the CSP and navigation rules of TECH01 §2.3 hold. Every command is declared through one macro that adds the `Authorized` extractor (webview label `main`, exact origin); a direct `#[tauri::command]` is a CI failure. A failed caller check, a `serde` parse failure, an unknown service id, a missing or unreadable setting all deny; nothing falls back to allow; errors carry a code and no detail.
> 6. **No network of Thermora's own** (TECH01 §7.2): no network crate, no updater, no telemetry; the only outgoing action is opening a fixed provider help page in the browser. The webview's own callouts are bounded as far as the OS allows and listed as residual risk.
> 7. **Nothing credential-like is logged or shown**; no log file exists until the design is amended (TECH01 §7.5).
> 8. The paths of TECH01 §12 (tier-2 paths) are human-gated; the Security owner co-approves their PRs.
